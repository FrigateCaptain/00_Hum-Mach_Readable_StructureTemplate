# Workflow: Формирование структуры workspace

## Назначение

Этот workflow — инструкция для LLM-ассистента. Он ведёт диалог с пользователем и на основе шаблонов из этого репозитория формирует или реструктурирует **всё** рабочее пространство пользователя (много папок, типы, реестры, план установки).

Длинный чеклист установки живёт **только в этом файле**. Skill `structure-workspace` (если есть в комплекте) только находит этот файл и исполняет его.

Смежные инструкции комплекта — **одна папка**, не весь workspace:

- `structure-template` — создать каркас или добавить только отсутствующие файлы; уже лежащий текст не трогать;
- `structure-revise` — ревизия, смена типа, переименование, разнесение, правки уже лежащих опорных файлов.

Перед запуском этого workflow пользователь должен был прочитать [`STRUCTURE_GUIDE.md`](../STRUCTURE_GUIDE.md) — хотя бы по диагонали — и иметь представление о типах папок и опорных файлах.

## Канон состава — с диска, не из памяти

Канон числа и имён файлов **не** хранится в этом workflow как заученный список.

1. Прочитать верхнюю секцию [`CHANGELOG.md`](../CHANGELOG.md) (`## [X.Y.Z]`). Сообщить номер версии одним предложением.
2. Прочитать [`STRUCTURE_GUIDE.md`](../STRUCTURE_GUIDE.md) целиком (этап 1) и раздел выбранного типа при работе с конкретной папкой.
3. Снять фактический состав каркаса: `find template/<тип> -type f` (пути от корня этого комплекта).
4. Если дерево типа в GUIDE не совпадает с `find` — остановиться и показать оба списка. Не выбирать молча.
5. Не восстанавливать каркас из памяти чата и не подставлять файлы «как обычно бывает».

Корнем комплекта считать каталог, в котором есть и `STRUCTURE_GUIDE.md`, и `template/`. Если этот workflow открыт не из той копии — спросить путь. Не выдумывать состав.

## Этап 1. Выяснение потребностей

Прочитай [`STRUCTURE_GUIDE.md`](../STRUCTURE_GUIDE.md) целиком. Затем спроси пользователя:

1. **Типы папок.** Покажи пользователю список шести типов (project, process, settings-n-servers, groundwork, meta-registry, storage) с краткими пояснениями. Спроси:
   - Все ли типы ему подходят и нужны?
   - Есть ли какие-то другие виды, которых здесь нет, но которые он хотел бы создать?

2. **Groundwork и RELEVANT_GROUNDWORK.md — обязательные элементы.** Папка типа groundwork и файл `RELEVANT_GROUNDWORK.md` входят в стандартный каркас шаблона (как `README.md`) и по умолчанию создаются. Не спрашивай, «нужны ли они». Уточни только частности:
   - Как назвать папку groundwork (или какое имя уже принято)?
   - Есть ли уже разрозненные наработки по workspace, которые стоит учесть?
   - Нужно ли сразу свести существующие наработки в groundwork, или пока зафиксировать отсутствие единой папки как временное состояние (с обязательным планом создать её)?
   - Есть ли пожелания к полям и содержимому `RELEVANT_GROUNDWORK.md` в папках типов project, process, storage, settings-n-servers и meta-registry (не к включению/исключению файла)?

3. **Дополнения и замечания.** Спроси:
   - Есть ли дополнения, замечания или пожелания к тем или иным типам?
   - Есть ли пожелания к составу опорных файлов конкретных типов или к их полям?

4. **Журналы.** Покажи матрицу:
   - project и process: `DECISION_LOG.md` и `WORK_LOG.md` обязательны (как `README.md`);
   - settings-n-servers, groundwork, meta-registry, storage: те же два файла — опциональный слот; уточни, заводить ли живой журнал;
   - process дополнительно: три опциональных слота `CYCLE_LOG.md` (исполнение цикла), `VERSION_LOG.md` (внутренние версии), `RELEASE_LOG.md` (внешние релизы). Имя слота можно выбрать при установке. Спроси, какие из трёх заводить.
   Не спрашивай, «нужны ли» обязательные журналы project и process. Уточни только, есть ли пожелания к полям записей.

5. **Контекст workspace.** Уточни:
   - Это новый workspace с нуля или реструктуризация существующего?
   - Какие LLM-инструменты используются?
   - Есть ли уже сложившиеся соглашения по именованию папок?

Дождись ответов на все вопросы, прежде чем переходить к следующему этапу.

## Этап 2. Формирование шаблона структуры

На основе ответов пользователя и типов из `STRUCTURE_GUIDE.md`:

1. Составь индивидуальный набор типов папок — с учётом того, какие стандартные типы пользователь принял, какие отклонил, какие хочет добавить. Groundwork и `RELEVANT_GROUNDWORK.md` входят в стандартный каркас по умолчанию. Журналы `DECISION_LOG.md` и `WORK_LOG.md` обязательны в project и process; в остальных четырёх типах — по ответу пользователя об опциональном слоте.
2. Для каждого принятого типа определи состав опорных файлов — с учётом пожеланий пользователя к полям и содержимому (включая пожелания к содержимому `RELEVANT_GROUNDWORK.md`, но не решение «включать или нет»: файл входит в стандартный каркас). Для process включи выбранные слоты `CYCLE_LOG.md` / `VERSION_LOG.md` / `RELEASE_LOG.md` или не копируй незаведённые. Состав имён файлов сверяй с `find template/<тип>`, не с памятью.
3. **Реестры.** Спроси пользователя, есть ли уже реестры, в которых перечислены все папки workspace с указанием назначения, описанием и статусом. Если пользователь не знает или реестров нет — просмотри workspace и предположи, где они могут находиться (типичные места: корень workspace, мета-папка, `registries/`). На основе результата определи, что нужно сделать с реестрами:
   - **есть и актуальны** — учесть их как источник истины при дальнейшей работе;
   - **есть, но неполные или устаревшие** — запланировать обновление;
   - **нет** — запланировать создание в рамках мета-папки.
   Мета-слой **не** создавать «заодно», если на этом этапе его не завели.
4. Покажи пользователю итоговый шаблон структуры в виде дерева и получи подтверждение.

## Этап 3. Планирование действий

Спроси пользователя:

1. **Анализ существующих папок.** Какие папки уже есть? Что ассистент уже видит в workspace? Что нужно просмотреть подробнее?

   Для **каждой** такой папки:

   - Определить тип комплексно, не по одному признаку:
     - состав файлов vs `find template/<тип>` шести типов GUIDE;
     - как папка отмечена в реестре папок workspace, если реестр есть (нет записи — так и сказать);
     - что написано в журналах (`DECISION_LOG`, `WORK_LOG`, `CYCLE_LOG`, `VERSION_LOG`, `RELEASE_LOG`) и в `CONTEXT.md` (журналов нет — так и сказать).
     Если пользователь явно назвал целевой тип — это целевой, даже когда состав и реестр ещё от другого (смена типа). Если целевой не назван и оси расходятся или картина смешанная — показать факты по трём осям и спросить. Если сомнений нет — назвать тип сразу и в скобках аргументы по каждой оси. Не угадывать.
   - Снять два списка: файлы папки и `find template/<целевой-тип>`.
   - Показать три колонки:
     - есть в шаблоне и в папке;
     - есть в шаблоне, в папке нет;
     - есть в папке, в шаблоне нет.
   - Для колонки «есть в обоих»: не планировать замену файла шаблоном. Если роль в GUIDE не совпадает с тем, что лежит в файле (например решения в `FACTS.md` вместо `DECISION_LOG.md`), предложить разнесение: какие фрагменты в какой файл, что остаётся.
   - Для колонки «есть в папке, в шаблоне нет»: не планировать удаление или перенос, пока пользователь не указал этот файл и действие.
   - В каком виде внести в реестр (если на этапе 2 заведён или уже есть meta-registry).

   Если папка **меняет тип** (не впервые получает тип) — дополнительно выполнить подэтап «Смена типа папки» ниже и включить его ответы в план.

2. **Создание новых папок.** Какие папки нужно создать прямо сейчас? Для каждой — уточни имя и тип.

3. Составь конкретный план работ. План — **список конкретных файлов и действий**, не общая фраза «привести к шаблону». В плане: что создать, что дополнить недостающими файлами, что разнести, что переименовать, что оставить лишним, что зарегистрировать в реестрах.

Покажи план пользователю и получи подтверждение перед выполнением. Ничего не переименовывать, не удалять, не сливать и не разносить по файлам, пока план не подтверждён.

### Смена типа папки

Отдельно от «просто добавить файлы нового каркаса».

1. Назвать исходный тип и целевой. Показать, какие слоты есть только у исходного, только у целевого, и какие совпадают по имени (`find template/<исходный>` и `find template/<целевой>`).
2. По каждому файлу, которого нет в целевом каркасе, или чья роль меняется, спросить **одним списком**, не молча выбирать:

   - **оставить** имя и место (лишний относительно нового типа файл остаётся);
   - **переименовать** в слот нового типа (указать новое имя);
   - **разнести** содержимое на несколько файлов нового типа (указать, какой раздел куда);
   - **сохранить копию** под прежним именем и завести новый слот отдельно;
   - **перенести** в другую папку / archive — только если владелец сам так сказал.

3. Совпадающие по имени файлы (`README.md`, `FACTS.md` и т.д.) не затирать шаблоном. Если границы ролей в GUIDE другие — предложить правки фрагментов, не замену файла целиком.
4. Выполнить только после ответов. Если на часть файлов ответа нет — эти файлы не трогать.

## Этап 4. Выполнение

Методично выполни **только утверждённый** план:

1. Создай папки и опорные файлы для новых сущностей. Placeholder шаблона заменить на содержание этой папки. Не копировать учебные блоки «Зачем нужен файл» как итоговый текст, если пользователь не просил оставить бланк. Опциональные слоты — только те, что выбраны на этапе 1–2; не создавать молча.
2. Дополни существующие папки **недостающими** файлами (колонка «есть в шаблоне, в папке нет»). Уже лежащие файлы с тем же именем **не затирать** шаблоном. Если в плане есть разнесение — выполнить только подтверждённые фрагменты. Текст, которому нет места в плане, не удалять: сначала спросить, куда его положить.
3. Лишние относительно шаблона файлы и папки для живой папки нормальны: не удалять и не переносить, если этого не было в подтверждённом плане.
4. Обнови реестры в meta-registry, **если** мета-слой заведён на этапе 2 или уже существовал. Не создавать мета-папку «заодно».
5. Ссылки в `RELEVANT_GROUNDWORK.md` — только в затронутых папках и только по плану.
6. Если состав файлов папки изменился — обновить `README.md` этой папки (что это, зачем, куда смотреть дальше).
7. По завершении каждого крупного блока — кратко сообщи пользователю, что сделано.

## Опорные принципы и последовательность отработки каждой папки

При отработке каждой папки опирайся также на критерии из раздела «Общие критерии качества структуры» ниже.

При формировании и оценке структуры придерживайся следующих принципов.

### Принцип 1. Сначала определить роль папки

Перед созданием структуры нужно ответить на один вопрос: это проект, процесс, настройки/серверы, groundwork, мета-реестр или хранилище. Ошибка на этом шаге обычно приводит к смешению документов и потере навигационной ясности.

### Принцип 2. Дать явную точку входа

У каждой значимой папки должен быть `README.md`, который отвечает минимум на три вопроса:

- что это за папка;
- зачем она существует;
- куда смотреть дальше.

### Принцип 3. Развести типы содержания по разным файлам

Не смешивать факты, планы, ограничения, backlog и инструкции в один длинный «универсальный» документ. Один файл должен отвечать за одну роль.

Решение (норма, которая могла быть иначе) → `DECISION_LOG.md`. Работа (кто сделал, какой артефакт) → `WORK_LOG.md`. Не смешивать решение и работу в одной записи.

### Принцип 4. Сделать канонические места хранения

Если факт относится к фактам, у него должно быть предсказуемое место хранения, например `FACTS.md`. Если задача отложена, она должна попадать в `BACKLOG.md`. Если нужен пошаговый порядок действий, он должен жить в `workflows/` или отдельном инструктивном документе. Если нужна связь с материалами groundwork — она живёт в `RELEVANT_GROUNDWORK.md` соответствующей папки, а не в копиях how-to.

### Принцип 5. Явно связать соседние сущности

Структура должна показывать связи ссылками: на связанные проекты, реестры, upstream/downstream-папки, публичные репозитории, материалы groundwork и ключевые документы.

## Общие критерии качества структуры

Эти критерии обязательны к применению на этапе «Опорные принципы и последовательность отработки каждой папки» — при оценке и формировании каждой папки.

- `Findability`: нужный файл можно найти по имени и месту без дополнительного объяснения.
- `Predictability`: одинаковые по роли папки и файлы устроены одинаково.
- `Traceability`: ясно, где канонический источник факта, а где ссылка или производное описание.
- `Separation of concerns`: факты, процессы, реестры, backlog и инструкции не смешаны в один неразборчивый документ.
- `Navigability`: из `README.md` можно дойти до ключевых документов без блуждания.
- `Maintainability`: структуру можно расширять без хаотического разрастания и без постоянных переименований.
