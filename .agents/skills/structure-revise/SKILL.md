# Ревизия и реструктуризация папки

Этот skill пригоден для любого workspace, где есть комплект Structure Template (`STRUCTURE_GUIDE.md` + `template/`).

Канон состава файлов **не** хранится в этом skill. Каждый раз читать диск: верхняя секция `CHANGELOG.md`, раздел типа в `STRUCTURE_GUIDE.md`, `find template/<тип>`.

Смежный skill `structure-template`: папка с нуля и только недостающие файлы без правок уже лежащего текста.

Установка или пересборка **всего** workspace — `structure-workspace` / `workflows/STRUCTURE_WORKFLOW.md`, не этот skill.

## Когда применять

- Ревизия: сравнить папку с каноном и показать расхождения.
- Реструктуризация или первичная структуризация уже наполненной папки.
- Смена типа папки.
- Правки в уже лежащих опорных файлах, связанные со структурой (роль файла, границы FACTS / журналов / backlog).

## Найти комплект шаблона

Искать каталог, в котором есть и `STRUCTURE_GUIDE.md`, и `template/`:

1. Корень, который пользователь указал явно.
2. Подняться от этого `SKILL.md` к родителям, пока не найдутся оба.
3. Папка, в имени которой есть `StructureTemplate` или `structure-template`.
4. Если не найдено — спросить путь. Не подставлять каркас из памяти.

## Общее правило диалога

Ничего не переименовывать, не удалять, не сливать и не разносить по файлам, пока владелец не подтвердил план. План — список конкретных файлов и действий, не общая фраза «привести к шаблону».

## Шаги ревизии

1. Прочитать верхнюю секцию `CHANGELOG.md`. Сообщить версию.
2. Зафиксировать текущий тип папки (как её ведут сейчас) и целевой тип (как должно быть). Если целевой не назван — показать шесть типов из GUIDE и спросить.
3. Снять два списка: файлы папки и `find template/<целевой-тип>`.
4. Показать владельцу три колонки:
   - есть в шаблоне и в папке;
   - есть в шаблоне, в папке нет;
   - есть в папке, в шаблоне нет.
5. Для файлов «есть в обоих» — не переписывать содержимое молча. Если роль в GUIDE не совпадает с тем, что лежит в файле (например решения в `FACTS.md` вместо `DECISION_LOG.md`), предложить разнесение: какие фрагменты в какой файл, что остаётся.
6. Дождаться ответа по плану. Затем выполнить только подтверждённое.

Недостающие файлы **без** правок уже лежащих можно создать в том же проходе, если владелец это подтвердил. Если задача была «только добавить бланки» — это `structure-template`, не этот skill.

## Смена типа папки

Отдельно от «просто добавить файлы нового каркаса».

1. Назвать исходный тип и целевой. Показать, какие слоты есть только у исходного, только у целевого, и какие совпадают по имени.
2. По каждому файлу, которого нет в целевом каркасе, или чья роль меняется, спросить **одним списком**, не молча выбирать:

   - **оставить** имя и место (лишний относительно нового типа файл остаётся);
   - **переименовать** в слот нового типа (указать новое имя);
   - **разнести** содержимое на несколько файлов нового типа (указать, какой раздел куда);
   - **сохранить копию** под прежним именем и завести новый слот отдельно;
   - **перенести** в другую папку / archive — только если владелец сам так сказал.

3. Совпадающие по имени файлы (`README.md`, `FACTS.md` и т.д.) не затирать шаблоном. Если границы ролей в GUIDE другие — предложить правки фрагментов, не замену файла целиком.
4. Выполнить только после ответов. Если на часть файлов ответа нет — эти файлы не трогать.

## Правки содержимого

Опираться на роли файлов в `STRUCTURE_GUIDE.md` текущей версии (FACTS vs DECISION_LOG vs WORK_LOG vs BACKLOG vs PLAN). Не смешивать решение и работу в одной записи. Не удалять текст, который некуда деть по плану, — сначала спросить, куда его положить.

## После подтверждённых изменений

- Обновить `README.md` папки, если состав файлов изменился.
- Если в этом workspace есть мета-реестр папок — обновить его только если владелец ведёт такой реестр; не создавать мета-слой «заодно».
- Если есть файл указателя на наработки (`RELEVANT_GROUNDWORK.md`) — поправить ссылки только в затронутых папках и только по подтверждённому плану.
